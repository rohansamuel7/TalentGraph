# Limitations and future work

TalentGraph is a local, evidence-based demonstration. Its outputs describe available text and modeled relationships, not people or hiring outcomes.

## Current limitations

1. **Bounded source.** **What it means:** The 1,500 LinkedIn postings are a repeatable selection from one local archive, not a statistically representative sample. The archive's exact published version has not been independently established. **Why it matters:** Results cannot describe the wider job market. **Future improvement:** Verify and version additional licensed sources, then choose a sampling method suited to the question being asked.
2. **Fictional candidates.** **What it means:** All 300 profiles come from synthetic role templates. **Why it matters:** Their scores say nothing about real applicants. **Future improvement:** If real profiles are ever used, establish consent, privacy safeguards, and a separate evaluation before interpreting results.
3. **Sparse technical evidence.** **What it means:** Of 1,500 postings, 80 have required technical evidence, 7 have preferred-only evidence, 44 have non-required-only evidence, and 1,369 have no eligible technical evidence. **Why it matters:** Missing evidence does not prove a skill is absent. For jobs without eligible required evidence, comparison is unavailable, not zero. **Future improvement:** Review more descriptions and improve coverage while keeping that unavailable state.
4. **Heuristic extraction.** **What it means:** Text rules and nearby words classify skill mentions as required, preferred, mentioned, negated, or ambiguous. This rule-based method can miss terms or misread context. **Why it matters:** A wrong classification can change a comparison. **Future improvement:** Expand the controlled skill vocabulary and test rule changes against reviewed descriptions.
5. **Limited human review.** **What it means:** People reviewed a small selected set of descriptions and found disagreements. **Why it matters:** That sample cannot establish accuracy across all postings. **Future improvement:** Review a larger, more varied sample and report errors separately for each classification.
6. **Comparison scope.** **What it means:** Required-skill overlap counts observed text evidence. It is not a hiring prediction, proficiency score, or measure of candidate suitability. A single observed requirement provides limited evidence; none leaves numeric overlap unavailable. **Why it matters:** Treating overlap as a hiring decision would overstate what the data supports. **Future improvement:** Keep explanations and evidence counts visible, and evaluate any new score against a clearly defined use case before using it.
7. **Legacy occupational categories.** **What it means:** M4 contains broad occupational and functional labels. They remain available to trace the source and in the M5 graph, but current matching and API graph views do not treat them as verified technical requirements. **Why it matters:** A job category could otherwise appear to be a skill the employer explicitly required. **Future improvement:** Keep those labels separate from reviewed, description-backed technical skills.
8. **Source-row traceability.** **What it means:** Spark processing indices and archive CSV record numbers come from different numbering methods. Their one-to-one match is unverified, although job IDs, source names, and description hashes are retained. **Why it matters:** A row number alone may point a reviewer to the wrong source text. **Future improvement:** Carry a stable archive record ID through sampling and Spark, then test it against job IDs and hashes.
9. **Local operation.** **What it means:** The API reads a database at a fixed local path and local JSON files. This is a prototype, not a deployed production data platform. It has no scheduled production runs, automated monitoring, deployment package, or independent clean-machine reproduction test. **Why it matters:** A successful local run does not guarantee reliable operation elsewhere. **Future improvement:** Test repeatable setup and recovery first, then add bounded scheduling, logs, and monitoring.
10. **Browser verification.** **What it means:** Code and production build checks exist, but some visual and interactive behavior still needs manual browser review. **Why it matters:** A passing build may miss unreadable controls or broken interactions. **Future improvement:** Add browser checks for themes, navigation, graph actions, and charts.

## Practical next steps

1. **Trace each source record.** Carry the archive's logical CSV record number through sampling and Spark. Check that it points to the same job ID and description hash before changing any existing row labels.
2. **Review more skill evidence.** Check a wider range of descriptions, especially cases where reviewers disagreed. Measure errors for each classification before changing extraction rules.
3. **Expand the data carefully.** Confirm the license and columns of each new source, record its version, and compare data quality across updates. Reconsider the sampling method before making claims about a wider population.
4. **Report data quality clearly.** Check source-to-curated record links, compatible file versions, unexpected missing values, and changes in evidence coverage. Set clear thresholds for failures.
5. **Prepare for regular runs.** Test new and changed inputs and recovery from failures. Then consider a small Airflow schedule (a tool for running tasks on a timetable), retries, run logs, and alerts.
6. **Check the complete user flow.** Add browser tests for navigation, themes, graph expansion, and charts. Measure performance with larger data and document the setup needed to deploy the app.
